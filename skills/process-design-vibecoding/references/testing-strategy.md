# Стратегия проверки

Локальное дополнение от 2026-10-05, выведенное из пользовательского `SKILL.md`.

Выбирать самый дешёвый уровень проверки, который подтверждает нужное поведение:

| Поведение | Подходящая проверка |
| --- | --- |
| Детерминированная бизнес-логика | Unit test с входом, результатом и крайним случаем |
| Ошибка в существующем коде | Воспроизведение и регрессионная проверка |
| Хранилище или граница компонентов | Интеграционная проверка состояния и ошибок |
| API | Запрос/ответ, права, ошибки и побочные эффекты |
| Критический пользовательский путь | Проверка полного пути в доступном окружении |
| Рефакторинг legacy | Характеризационные или контрактные проверки до изменения |
| Визуальная правка | Осмотр результата в нужных размерах и состояниях |

Для новой бизнес-логики и исправлений предпочитать RED → GREEN → refactor:
сначала воспроизвести ожидаемое падение, затем внести изменение и запустить
связанные проверки. Не заявлять TDD, если тест не запускался до реализации.

Для исследовательского прототипа, визуального поиска или недоступной внешней
системы заранее назвать практический способ проверки. Не строить тестовую
инфраструктуру, если она превышает область небольшой задачи.

Проверять значимые успешные и ошибочные сценарии, права и повторы там, где они
влияют на результат. Не писать тесты, повторяющие структуру реализации.

После успешных достаточных проверок расширять их только при новых изменениях
или нерешённом риске. Smoke test не доказывает полный пользовательский сценарий.
Фиксировать точные команды, исход и реальную границу покрытия.
