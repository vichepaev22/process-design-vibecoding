# Изменение требований

## Основное ТЗ

В начале работы определить точный путь или идентификатор основного ТЗ. Сохранить
существующее `PRD.md`, `spec.md` или документ проекта. Дополнительный план,
дизайн или запись в чате дополняет ТЗ и не заменяет его. Не создавать второе
основное ТЗ из-за отличающегося имени или формата.

## Статусы и разрешение

Каждое существенное предложение сохранить с устойчивым ID и статусом:
`proposed` — предложено, `accepted` — принято, `deferred` — отложено,
`rejected` — отклонено. Отдельно вести состояние выполнения:
`pending`, `implemented`, `verified`. Принятое требование ещё не означает,
что оно реализовано или проверено.

Явное указание пользователя «добавь», «сделай», «давай реализуем» разрешает
описанное изменение в его области. Вопрос «можно ли» или идея без решения
остаётся предложением. Не согласовывать повторно уже разрешённое действие.
Не включать предложенную идею в принятый объём молча. Сохранить отложенные
предложения вместе с причиной или условием возврата к ним.

## Порядок изменения

1. Записать исходный запрос, его ID, статус и новое ожидаемое поведение.
2. Оценить только значимое влияние: данные, API, права, миграция, UX, проверки,
   стоимость и объём работы.
3. Для принятого изменения **сначала обновить основное ТЗ**. В текущем разделе
   должен остаться действующий вариант требования. Старый вариант при
   необходимости перенести в явно помеченную историю. Сохранить совместимые
   ранее принятые решения.
4. Обновить сценарии приёмки: кто действует, при каких условиях, какой результат
   и ограничения ожидаются.
5. Связать требование с задачей в плане, затем менять реализацию.
6. Запустить соразмерные проверки. Не ослаблять валидный тест ради зелёного
   результата; при изменении требования записать основание изменения теста.
7. Перед завершением сверить **каждый существенный запрос текущей задачи**:
   он отражён в основном ТЗ либо имеет явный статус предложения, отсрочки или
   отказа. Для принятого требования указать приёмку, состояние выполнения и
   фактический результат проверки.

Например, поручение «уведомляй получателя после подтверждённого начисления»
нельзя оставить только в плане админки. Требование должно появиться в основном
ТЗ с условиями подтверждения, адресатом, защитой от повтора и сценарием приёмки.

Короткая квитанция изменения достаточна:
`CR-003 → docs/PRD.md: ADM-003 → AC-003 → TASK-003 → pending`.
Одна строка может ссылаться на принятый формат проекта; новый журнал не обязателен.

## Работа с документами в ChatGPT

Определить основной документ или вложение. Если доступен разрешённый инструмент
редактирования, сохранить изменение и проверить результат. Если доступа нет,
выдать обновлённый документ или точный патч и сообщить, что исходный документ
ещё не обновлён. Не говорить «добавлено в ТЗ», если обновлён только текст в чате.

## Необязательный машинный журнал

Шаблон `assets/change-ledger-template.json` подходит, если проекту нужен
проверяемый журнал. Пример принятого изменения:

```json
{
  "changes": [
    {
      "id": "CR-003",
      "summary": "Notify the recipient after a confirmed credit grant",
      "status": "accepted",
      "delivery": "pending",
      "spec_ref": {"path": "docs/PRD.md", "marker": "ADM-003"},
      "acceptance_ref": {"path": "docs/acceptance.md", "marker": "AC-003"},
      "plan_ref": {"path": "docs/plan.md", "marker": "TASK-003"}
    }
  ]
}
```

```bash
python scripts/validate_project_memory.py --root /path/to/project \
  --spec docs/PRD.md --changes docs/changes.json --require-change CR-003
```

Запускать скрипт из каталога навыка либо указывать полный путь к нему. Пути
документов в журнале относительно корня проекта. Существующий формат ТЗ можно
выбрать через `--spec`; остальные структурные проверки относятся к шаблонам
этого пакета. Использование скрипта не требует переформатировать чужой проект.

Проверка выявляет отсутствующие ID, ссылку на дополнительный документ вместо
основного ТЗ, отсутствующие маркеры и статус `verified` без записи результатов
в `verification`. Она не доказывает смысловую полноту требования и не исполняет
записанные команды проверки. Эти два пункта агент проверяет отдельно.

Мелкое уточнение, не меняющее поведение, не требует отдельного журнала,
повторного discovery или большого набора тестов.
